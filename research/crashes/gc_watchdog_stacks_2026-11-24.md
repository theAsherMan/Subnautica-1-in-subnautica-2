  - **Engine source of the purge loop (VERIFIED 2026-11-25, read in `<ModkitDir>/UE_5.6_SN2/Engine/Source`; replaces the 2026-11-24 planner caveat). The slow purge is a busy-poll of not-ready objects, not FinishDestroy work.**
    - `IncrementalDestroyGarbage` (`Runtime/CoreUObject/Private/UObject/GarbageCollection.cpp:4721`): the first pass calls `IsReadyForFinishDestroy()` on every unreachable object; ready ones get `ConditionalFinishDestroy`, not-ready ones go to `GGCObjectsPendingDestruction`. The deferred loop (line 4821) re-polls the whole pending list, swap-removes the ready ones, and in a full (non-time-limited) purge calls `FPlatformProcess::Sleep(0)` after each pass (line 4963). So the `this` objects changing between stack samples is the re-poll walking the list, not proof of progress (the 2026-11-24 "making progress, 0.77 ms per object" reading above is withdrawn).
    - Timeout (line 4909) fires only when one pass made zero progress AND `Seconds() - LastTimeoutWarningTime > MaxTimeForFinishDestroy` (`LastTimeoutWarningTime` starts at the function start). Default cvar 10 s (line 4705); the game config sets 20. It logs the first 10 not-ready objects (`GMaxFinishDestroyTimeoutObjectsToLog = 10`, line 349), then `AbortInsideMemberFunction`. `gc.AdditionalFinishDestroyTimeGC` (40) applies only on iOS/Android. **So "objects in queue: ~22.8k" = objects still NOT ready after 20 s, with no progress in the last pass.**
    - `FRenderCommandFence::IsFenceComplete` (`Runtime/RenderCore/Private/RenderingThread.cpp:1110`) calls `CheckRenderingThreadHealth()` (line 875) on every call; on the game thread that runs `GLog->FlushThreadedLogs` and `FPlatformApplicationMisc::PumpMessages(false)`. So every poll of a fenced object goes through `PeekMessageW` and the Steam overlay hook: this explains the RIP split (gameoverlayrenderer64 33, USER32 33, ntdll yield/SRW 69). Mapping, **LOGGED (2026-11-25, inference from stacks + source, no PDB):** 0x32BF240 (0x6B bytes, on the chain in 67 %) = `IsFenceComplete` / `CheckRenderingThreadHealth`; 0x32B22C0 = the PumpMessages side; 0x149A6F0 = the `Sleep(0)`/yield wrapper; 0x4605AF0 = an `IsReadyForFinishDestroy` override.
    - Fence bundler: `StartRenderCommandFenceBundler` / `StopRenderCommandFenceBundler` are bound to `PreGarbageCollectConditionalBeginDestroy` / `PostGarbageCollectConditionalBeginDestroy` (`Launch/Private/LaunchEngineLoop.cpp:3651`, broadcast in `UnhashUnreachableObjects`, `GarbageCollection.cpp:6065/6133`); `FRenderCommandFence::BeginFence` (`RenderingThread.cpp:1036`) with `ESyncDepth::RenderThread` reuses the bundled event. So all BeginDestroy fences of the purge share one render-thread event that is dispatched before the purge loop starts.
    - What each sampled class waits on: `UPrimitiveComponent::IsReadyForFinishDestroy` (`Engine/Private/Components/PrimitiveComponent.cpp:1928`) = `Super && DetachFence.IsFenceComplete()` (AActor, LightComponent, SkyLightComponent, Model, MapBuildData use the same pattern) → a SphereComponent/StaticMeshComponent waits ONLY on a render fence. `UStreamableRenderAsset` (`Engine/Private/StreamableRenderAsset.cpp`): `BeginDestroy` (455) calls `CancelPendingStreamingRequest()`, `IsReadyForFinishDestroy` (469) ticks `PendingUpdate` (TT_GameRunningAsync or TT_None) and returns `!PendingUpdate.IsValid()`. `UStaticMesh::IsReadyForFinishDestroy` (`StaticMesh.cpp:5788`): Super, then `HasPendingInitOrStreaming()`, then ReleaseResources, then `ReleaseResourcesFence.IsFenceComplete()`. `FRenderAssetUpdate::Tick` (`Engine/Private/Streaming/RenderAssetUpdate.cpp:173`) uses `CS.TryLock` for TT_None. `TRenderAssetUpdate::TickInternal` (`Engine/Internal/Streaming/RenderAssetUpdate.inl:38`) returns Suspended while `TaskSynchronization > 0` (pending IO), schedules GameThread steps as TaskGraph GameThread tasks (`FRenderAssetUpdateTickGTTask`; returns InProgress while one is scheduled) and render steps via ENQUEUE_RENDER_COMMAND.
