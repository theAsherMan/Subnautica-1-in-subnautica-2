# GC-watchdog crash (lobby to world load) - OPEN

Summary of the open crash. Instances and ending variants: `gc_watchdog_instances.md`. The full hypothesis chain H1-H8 and every update (old step 0b, verbatim): `gc_watchdog_plan_history.md`. Pass-1 text of this file: `git show 3449200:research/crashes/gc_watchdog.md`.

## Summary — OPEN (2026-11-14)

- **Symptom:** loading from the lobby into a world (`L_Main`, also `L_SN2World`) can end in a GC watchdog crash after about 20 s in the lobby purge ("Spent more than 20.00s on routing FinishDestroy"). Frequency LOGGED 2026-11-23: 4/49 logged loads on L_SN2World (2026-11-22 harness, 2026-11-23 user load, two 2026-11-23 harness runs that wrote a dump and then hung instead of exiting). The purge time is continuous (median 0.13 s, 15/53 at 10 s or more); every long purge came < 52 s after the lobby LoadMap started, every later load purged in <= 0.3 s (LOGGED 2026-11-23).
- **Status:** NOT fixed. Crashed again 2026-11-18 with all our Lua mods disabled, so our polling is not the cause. User decision 2026-11-18: the "wait 60 s at the menu" workaround is withdrawn (the 11-17 17:27:51 crash came ~59 s after the menu); this is a bug to fix. The UE4SS on/off A/B (rename `dwmapi.dll`) was never completed.
- **Related crashes on `L_SN2World`, 2026-11-22 spot1 runs:** lobby-teardown stall then 0xC0000005 write (run 163326) = this bug; READ AV in `UE4SS.dll` (run 164700) = the removed SN2AutoTest PODDUMP (`research/process/core_rules.md` "Crashes"). The harness classifies both as CRASH.
- **Boot time predicts the purge (LOGGED 2026-11-23, 55 loads):** boot -> lobby <= 16 s (warm cache) always purged <= 0.06 s; every purge >= 10 s and all 3 crashes had boot -> lobby >= 23.7 s (crashes 38.9 / 41.8 / 28.4 s). Back-to-back runs warm the cache, so a sequential 5 ON + 5 OFF A/B is confounded: alternate arms and compare purge vs boot time.
- **Purge facts:** the purge is the gap `Audio Device unregistered from world 'None'` -> `SkyLight change`; measure it per load (`src/tools/gc_purge_stats.py`). The slow purge is game-thread work (GameThread 99.7 % busy, other threads idle; VERIFIED for one sampled run 2026-11-24, `20261124_190357_gc_ab_ON_1`). The lobby has only 32 live SphereComponents (LOGGED 2026-11-23), so the ~22.8k watchdog objects are invisible to `FindAllOf`.
- **Engine source read (VERIFIED 2026-11-25):** the slow purge is a busy-poll; the ~22.8k "objects in queue" are objects still NOT ready after 20 s; components wait only on render fences (DetachFence), meshes/textures on stream updates + fences. The timeout fires on one zero-progress checked pass after 20 s from purge start.
- **First sampled crash (LOGGED 2026-11-25, run `20261125_162524_gc_ab_ON_2`):** queue 22798 = ~11.4k SphereComponents + their Blueprint-class objects waiting on DetachFence; every other engine thread stayed blocked in one kernel wait (VERIFIED from registers); the render thread blocks 6-15 s inside one render command.
- **H6 / H7 (LOGGED 2026-11-25):** the fence is NOT lost (H5 "bundler left open" FAILED, H6 "InsertFence stranded in `FRenderThreadCommandPipe`" refuted). The blocking command is a `DeleteResource` of a **streaming virtual texture**: `FVirtualTexture2DResource::ReleaseRHI` -> `ReleaseVirtualTextureProducer` -> `FVirtualTextureProducer::Release` -> `WaitUntilTasksComplete` on the producer's transcode/read tasks; only the GameThread runs during the stall. The game is on a 7200 rpm SATA HDD (VERIFIED 2026-11-25).
- **Current explanation H8 (LOGGED 2026-11-26, supported not proven):** the lobby IO is vanilla IoStore reads of `Subnautica2-Windows.ucas` (VERIFIED): at the title screen one burst of ~1,310 priority -1 (`AIOP_BelowNormal`) bulk reads (345 MB, mesh LOD / texture mip `.ubulk`) plus 1,200-1,600 `AIOP_Low` reads, served from the HDD at 12-20 MB/s. The purge ends within 0.2 s of the BelowNormal queue emptying in 5 of 5 sampled runs, incl. one GC_CRASH; the stall is the drain time of that queue (6 s warm cache, 17-37 s cold). D: was 0 % idle through the purge in run 175756 (VERIFIED 2026-11-25). VT high-priority tile reads are BelowNormal too, so the VT release most likely waits behind that burst (producer identity not proven). Not run: vanilla comparison.
- **Candidate fixes (UNTESTED, planner decides):** (1) raise `r.VT.IOPriority_HighPagePri` above BelowNormal before the title screen (`gc_ab_test.sh --vt-prio 3`); (2) find and cut what the title screen loads. Engine GC cvars are excluded as a fix. None applied.
- **Fix-1 setup (LOGGED 2026-11-26):** three boot crashes during setup were an unguarded `FindFirstOf(...):GetWorld()` in the test-only `vtprio.lua` (fixed; run `20261126_181446_gc_ab_ON_1` = VT_PRIO_OK). The cvar reads 2 (BelowNormal) at mod start. Fix 1 itself is UNTESTED.

## Dead ends
- **FAILED (2026-11-18)** "our Lua polling in the lobby causes it": crash with all Lua mods off; hot reload on/off made no difference.
- **FAILED (2026-11-24)** `LogGarbage Verbose` and `-trace`: do not work in Shipping builds.
- **FAILED (2026-11-25)** H5, the render command bundler left open: bundler globals read from memory showed depth 0 / event unset the whole purge.
- LOGGED 2026-11-24: the ~22.8k queue is not a SphereComponent set (only 148 exist, all unflagged at travel time); lobby total ~200k live objects, none from our mods.
- LOGGED 2026-11-24: the partial A/B (8 cold-cache runs, cancelled by the user: ON 2 GC_CRASH + 1 DONE + 1 TIMEOUT, OFF 3 DONE with purges of 15-18 s) was too small to separate the arms.
- LOGGED 2026-11-25: all-thread series runs 1-2 timed out while still loading (boot -> lobby 80-93 s); per the project owner slow-load timeouts are PASSes.
