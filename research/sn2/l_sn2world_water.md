## Root cause of the zero water volume (Phase B, 2026-11-19)
Evidence: `<ModkitDir>\ocean_t3d_*.t3d`, `scratch_bp\ocean_json\BP_Ocean.json`, `scratch_bp\sn2w_json\L_SN2World.json`.
1. `BP_Ocean_C::UserConstructionScript` = `WaterVolumeComponent.K2_SetRelativeLocation(Vector_Down * (BodySize.Z * 50), ...)`, then `SetRelativeScale3D(BodySize)`, then `UpdateOcealnLevelMPC()` (VERIFIED).
2. `BodySize` is a C++ member of `AUWEWaterBodyOcean`; the BP CDO reads (1e6,1e6,1e5), instances read 0; **it is not serialized**, so the construction script zeroes the WaterVolumeComponent scale at cook.
3. BodySize 0 gives exactly the broken state. Our cooked L_SN2World contains the zero (export 34 `BP_Ocean_C_0.WaterVolumeComponent` `RelativeScale3D IsZero: true`).
4. L_Main's cooked ocean has the bake (0,0,-5e6)/(1e6,1e6,1e5) while its instance BodySize is also 0. LOGGED/UNTESTED hypothesis: WP maps are cooked without re-running the construction script.
5. Modkit game code is stubs (`<ModkitDir>\Subnautica2-Project\README.md` L15; `Plugins\UWEWater\` has only the .uplugin), so the real C++ probably sets BodySize before the BP script (UNTESTED, more likely). Catch-all risk: any copied BP actor whose construction script reads a C++-computed value can bake wrong.
6. The origin `BP_BoxVolume_C` ("BP_AirVolumeAboveOcean", scale 100000) is the air counterpart (`VolumeData=(VolumeType=EVolumeType_Air,Priority=10,EnvironmentType=EnvironmentType.Air)`), not the swim volume; L_Main has 3 `BP_BoxVolume_C` and 0 `PhysicsVolume`. Water state comes from the ocean region's VolumeTracker BoxVolumeComponents.
Fix applied: a standalone `BP_UWEOceanBiomeRegionActor_C` at (0,0,-5e6) scale (1e6,1e6,1e5) plus the origin air volume (next sections).

  - REJECTED 2026-11-19 — `SN2WaterFix`, a runtime Lua mod re-setting BodySize at launch (deleted, never installed): the owner wants the map fixed at source.
  - FAILED 2026-11-19 — `20261119_201024_lmain_baseline` FAIL_LOBBY: Lua load error at `SN2AutoTest/Scripts/main.lua:215` ("unfinished string near '"['", a raw CR/LF/TAB in a Lua pattern in `shortErr`; guard in `research/process/README.md`). `20261119_201610` and `20261119_201807` FAIL_MENU (save_list fingerprint mismatch, d=0.602, from extra save slots and the shader counter).

## Region water volume in L_SN2World: SOLVED (2026-11-27; investigator-water2/3/4, implementer-water/water2/water3)
Symptom was: orange rock, no blue underwater fog in L_SN2World although every region carried the baked MIC. Now blue like L_Main.

**Recipe (current state)**
1. **The water look is a VOLUME-domain material.** `M_OceanVolume` (`MaterialDomain = MD_Volume`) on region cube meshes, injected into volumetric fog. VERIFIED (2026-11-27, cooked export via retoc + uaa.exe). Hiding the region meshes in L_Main removes the blue fog (VERIFIED, `20261127_174548_uwab_lmain`).
2. **Baked MICs carry the values.** `src/modkit/scripts/sn2world_water_mats.py` makes `/Game/Mods/SN2EmptyWorld/WaterVolume/MI_WV_Ocean` (L_Main values) and `MI_WV_SS_000..041` (parent `/Game/Materials/Water/MI_OceanVolume`). VERIFIED as data (2026-11-27, `uwa1` effective-value walk). The MIC values alone do not make the water draw.
3. **The tracker's slot 15 must belong to a valid, sized ocean volume.** `UWEBiomeTrackerSubsystem` re-sorts the volumes; `CurrentWaterBodyIndex` = the volume's sorted slot, slots 0..14 = the 15 nearest local volumes, slot 15 is reserved for one ocean-type volume (the last registered wins). In the map, `BP_Ocean_C_0.WaterVolumeComponent` spawned a zero-scale child region `CAT_0` that took slot 15, so the cube had nothing to draw. Fix at source: `sn2world_ocean_slot.py` sets `child_actor_class = None` on that component, which PERSISTS. VERIFIED (2026-11-27, editor reload; game `uwa21` row: standalone ocean region `idx=15`).
4. **`BiomeRegionVolumeType` must be 1 (BRVT_Shape) on the ocean region, and it cannot be saved in the map.** The editor's stub C++ class default is Shape; the shipped game's default is Brush. A saved Shape equals the editor default, so it is never serialized and the game loads Brush (run `20261127_204728_uwconfirm_sn2`: all regions volType=0 in game while the editor T3D showed no VolumeType line). **Fix: runtime set from the cooked ModActor graph** (`src/modkit/scripts/sn2emptyworld_graph.py`, L_SN2World branch): `GetAllActorsOfClass(BP_UWEOceanBiomeRegionActor_C)` -> `ForEachLoop` -> `KismetSystemLibrary.SetBytePropertyByName(Object, "BiomeRegionVolumeType", 1)`, then destroy self. This is cooked mod content (Blueprint graph), not a Lua patch.
5. **Confirmation. VERIFIED (2026-11-27, run `20261127_211152_uwconfirm_sn2`: hidden, engine input, DONE, no new save slot, no in-memory patch).** `uwa21`: `BP_UWEOceanBiomeRegionActor_C_3 idx=15 order=43 volType=1 blendType=1 blendDist=1000 fogW=1` (43 regions). Shots `00_pod_underwater_side_k0.png` (2 m): saturated deep-blue water filling the upper half with surface cloud patterns, dark blue-navy haze toward the horizon, orange-brown rock dissolving into blue fog with distance; `02_natures_table_k0.png` (11 m): deep blue water, brown rock arch in the mid-ground tinted blue-dark by distance. Compared with the in-memory reference `20261127_190333_uwab_sn2k/shots/02_c_volType1_k0.png` (same pose, 2 m): the same blue water look (reference additionally has air bubbles from the camera; nothing else differs). The rock stays orange-brown (terrain material, same in the reference).

LOGGED (2026-11-27, same run):** all 42 `BP_UWEWaterBiomeRegionActor_C` boxes show `volType=0` in game (Brush) with `ppW=0`; no visible difference in the shots between positions near and far from boxes; the plan has no `uwa1`, so the boxes' MID values were not re-read in this run (last read: baked MI_WV_SS_* values resolve, see item 2).
