## Parallel sessions: the heavy lock (`src/tools/heavy_lock.sh`, built 2026-11-19)
RAM fits only one heavy job at a time, so several Claude sessions share a single lock. Which jobs are heavy is listed in `CLAUDE.md` "Parallel sessions: one heavy job at a time" (the single source of truth; changing it also means updating `SN2_HEAVY_PROCS` in `heavy_lock.sh`). SN1 launches were added by user rule 2026-11-22; `sn1_run.sh` takes the lock as `sn1`.
- **Commands:**
  - `bash src/tools/heavy_lock.sh status` shows the holder, the running heavy processes and a verdict (FREE / HELD / BUSY).
  - `acquire <game|editor|cook|build|sn1> [--wait S] [--note T]`: exit 0 means this session holds the lock. `--wait` polls every `SN2_LOCK_POLL` s (default 15). Run long waits with `run_in_background: true`. Re-acquiring a lock you hold refreshes it and adds `<what>`.
  - `release [--force]`: `--force` takes another session's lock and needs the user's say-so.
  - `check`: exit 0 if this session holds the lock (also renews the lease).
  - `renew`: holder only, resets the lease (exit 1 if not yours). `hold [--every S] [--max S]`: holder only; a foreground heartbeat (run it with `run_in_background: true`) that renews every S s (20) for at most `--max` s (3600), and ends by itself when you released, lost the lock or your claude.exe is gone. Use it across a long job that is not a heavy process (Python extractor) or a long gap between steps.
- **State and identity:**
  - The lock lives in `<Workspace>/locks/heavy.info`, as key=value lines: owner, owner_pid, what, note, since, seen, renewed. Waiters queue as files in `<Workspace>/locks/queue/` (name `<epoch-ns>.<owner>`, content owner, mtime = last poll).
  - Every read-modify-write runs under an atomic `mkdir` guard, `.guard`. A guard older than 60 s is removed.
  - Events are logged to `<Workspace>/locks/history.log`.
  - `SN2_LOCK_DIR` overrides the folder, for tests.
  - The owner is `SN2_LOCK_OWNER` (PID in `SN2_LOCK_OWNER_PID`), otherwise `claude-pid-$CLAUDE_PID`. Each Claude session is its own claude.exe; in-process subagents share their parent's lock.
- **The lock counts as free when any of these holds (lease design, 2026-11-28):**
  - nobody holds it
  - the holder's `owner_pid` process is gone: freed at once. `owner_pid` is the claude.exe of a normal session; a named owner (`SN2_LOCK_OWNER=<agent>`) has none unless `SN2_LOCK_OWNER_PID` is set, so subagents rely on the lease below
  - lease expired: no heavy process running and no renewal (`acquire` by the holder, `check`, `renew`, `hold`) for `SN2_LOCK_IDLE` s (default 600). This frees a holder that forgot to release within 10 min. A holder whose heavy process is running is never idle, so gaps up to 10 min between your own steps (install, launch, read results, edit, relaunch; editor script, cook) keep the lock; for longer gaps or Python jobs run `hold` in the background.
  - History: the lock was 600 s until 2026-11-19, 60 s, then 10 s on 2026-11-28; 10-60 s lost the lock in the gaps between a session's own steps (`history.log` 13:23-13:57 showed two sessions alternating TAKEOVER every 15 s, each cutting the other's multi-step job).
- **Unowned heavy processes:** if nobody holds the lock but a heavy process is running, the verdict is BUSY. This catches an orphan or a game or editor started by hand. Only `acquire editor` may adopt an already-open UnrealEditor / ShaderCompileWorker.
- **Stopping a waiter can still leave you holding the lock (seen twice, 2026-11-28 12:19 and 16:51:37):** a background `acquire --wait` that is stopped (TaskStop) just as it is granted leaves the lock HELD by your owner, with nothing running. After stopping a waiter, always run `status`; if you are the holder, `release` (with the same `SN2_LOCK_OWNER`). A dead waiter's queue entry stays listed until it is pruned (max(4*POLL, 60) s).
- **Fair order:** `acquire --wait N` (N>0) joins a FIFO queue and keeps its place on every poll; an entry not refreshed for `SN2_LOCK_QTTL` s (max(4*POLL, 60)) is dropped as dead. While a live waiter is queued, nobody else can take a free or stale lock: a `--wait 0` caller (newcomer, or the releasing holder re-acquiring) is refused (exit 1, so callers' exit 4 / 2 paths are unchanged) and the queue head takes it at its next poll (at most `SN2_LOCK_POLL` s).
- **Replacing the script safely:** the whole script is one function called on the last line. Write a temp file next to it and `mv` it over `heavy_lock.sh` (never edit in place); running copies keep the old inode. VERIFIED (2026-11-28): an old-version `acquire --wait` loop survived an `mv` over its script and later acquired the lock. Old loops still apply the old 10 s idle rule until they end (they ignore `renewed`, but `renew`/`hold` also write `seen`, which they honour).
- **Gap: subagents share their parent's lock identity. FAILED (2026-11-26, runs `autotest/20261126_191722_samples` and `20261126_191727_brownwater_pp`):** the owner id is `claude-pid-<CLAUDE_PID>`, and an in-process subagent has the same claude.exe pid as the session that spawned it. The planner held the lock (`acquire game`) and started a samples autotest; 5 s later its investigator subagent's `autotest.sh` "acquired" the same lock (same owner) and launched a second game. Both runs ended `FAIL lobby not reached` (19:22:41). Rule until a code fix: a subagent that may run heavy jobs sets its own `SN2_LOCK_OWNER=<agent name>` on every heavy command, and the parent does not start heavy jobs while such a subagent is running. Still open (UNTESTED idea): `acquire` by the same owner refuses while a heavy process is running that this command did not start.
- **Heavy process names:** image-name prefixes in `SN2_HEAVY_PROCS`, default `Subnautica2-Win64 UnrealEditor AutomationTool UnrealBuildTool UnrealPak ShaderCompileWorker sn1build Subnautica.exe` plus `dotnet.exe` running AutomationTool/UnrealBuildTool (SN1 counts as heavy; a hand-started SN1 game makes the verdict BUSY). **Python jobs (e.g. `sn1_extract_terrain.py`) are not heavy processes by image name:** they keep the lock only through the lease or `hold` (run `heavy_lock.sh hold` in the background for jobs over a few minutes).
- **Wired into:**
  - `launch_game.sh`: acquire game, exit 4 if busy. `relaunch_on_exit.sh` goes through it and re-acquires as the same owner.
  - `install_mod.sh`: acquire game, exit 4. The mod files in `<GameDir>` are shared state.
  - `autotest.sh` and `autotest_retry.sh`: wait up to `SN2_LOCK_WAIT` s (default 3600), exit 2 on timeout, release on exit. A run inside autotest_retry reuses the held lock.
  - `src/modkit/tools/cook_install.sh`: what=cook, waits like autotest, exit 4.
  - `src/modkit/tools/launch_editor.sh`: acquires editor, then starts `Launch-Editor.cmd` unless an editor is already open.
  - `ue_run.py`: exit 5 if this session does not hold the lock. `SN2_LOCK_SKIP=1` bypasses the check.
  - Double-clicking `Launch-Editor.cmd` bypasses the lock, but the running editor still makes other sessions wait.
- **Rules:**
  - Acquire before starting a heavy job.
  - Close what you started: quit the game, or close the editor (`ue_run.py -c "unreal.SystemLibrary.quit_editor()"` is UNTESTED).
  - Then `release`. Releasing while heavy processes still run prints a WARNING, and other sessions stay BUSY until those processes exit.
- **Not covered by the lock:** the modkit project content (two sessions editing assets between editor runs), SN2 saves, and `mods.txt` edits made outside install_mod.sh. Each session installs its mods right before it launches, as autotest does.
