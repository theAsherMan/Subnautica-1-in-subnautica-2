# Runbook — how to change the game and test it

## The loop (every change)
1. Edit `src\mods\<Mod>\Scripts\main.lua` (and `data\` files). For large edits, write a small Python patch
   script that asserts its anchor strings occur exactly once, then replaces — this caught several mismatches.
2. Install: `bash src/tools/install_mod.sh <Mod>` (copies Scripts + data into the game and the bundle, registers in `mods.txt`).
3. **UE4SS reads Lua only at game launch.** Reloading the save does NOT pick up changes. Hot-reload is deliberately OFF (see Crashes).
   If the game is running: start `bash src/tools/relaunch_on_exit.sh` with `run_in_background: true`, then ask the tester to quit.
   It relaunches via `launch_game.sh` (Steam `-applaunch`, see "Launching through Steam" below) after a confirmed exit. If not running: `bash src/tools/launch_game.sh`.
4. Watch the log with the Monitor tool: command `bash src/tools/watch_log.sh`, `timeout_ms: 1800000`; re-arm on expiry.
   Monitors die when the Claude session restarts — re-arm after any restart. Keep the filter quiet (per-sweep lines flood the chat).
5. The tester loads the save and presses keys; you read results from the log and ask the tester what is visible. The log proves calls ran, only the tester can confirm visuals/physics.

## Parallel sessions: the heavy lock (`src/tools/heavy_lock.sh`, built 2026-11-19)
RAM fits only one heavy job at a time, so several Claude sessions share a single lock. Heavy jobs are the game, the modkit editor, a cook, Subnautica 1 (any SN1 launch; `sn1_run.sh` takes the lock as `sn1`; user rule 2026-11-22), and the SN1 builder / terrain extractor.
- **Commands:**
  - `bash src/tools/heavy_lock.sh status` shows the holder, the running heavy processes and a verdict (FREE / HELD / BUSY).
  - `acquire <game|editor|cook|build|sn1> [--wait S] [--note T]`: exit 0 means this session holds the lock. `--wait` polls every `SN2_LOCK_POLL` s (default 15). Run long waits with `run_in_background: true`. Re-acquiring a lock you hold refreshes it and adds `<what>`.
  - `release [--force]`: `--force` takes another session's lock and needs the user's say-so.
  - `check`: exit 0 if this session holds the lock.
- **State and identity:**
  - The lock lives in `<Workspace>/locks/heavy.info`, as key=value lines: owner, owner_pid, what, note, since, seen.
  - Every read-modify-write runs under an atomic `mkdir` guard, `.guard`. A guard older than 60 s is removed.
  - Events are logged to `<Workspace>/locks/history.log`.
  - `SN2_LOCK_DIR` overrides the folder, for tests.
  - The owner is `SN2_LOCK_OWNER` (PID in `SN2_LOCK_OWNER_PID`), otherwise `claude-pid-$CLAUDE_PID`. Each Claude session is its own claude.exe; in-process subagents share their parent's lock.
- **The lock counts as free when any of these holds:**
  - nobody holds it
  - the holder's claude.exe is gone
  - no heavy process has run for `SN2_LOCK_IDLE` s (default 60, cut from 600 on 2026-11-19 by user request) since the later of `since` and `seen`. Gaps longer than that between your own steps (install, then launch; quit, then relaunch) lose the lock, so do them back to back
- **Unowned heavy processes:** if nobody holds the lock but a heavy process is running, the verdict is BUSY. This catches an orphan or a game or editor started by hand. Only `acquire editor` may adopt an already-open UnrealEditor / ShaderCompileWorker.
- **Heavy process names:** image-name prefixes in `SN2_HEAVY_PROCS`, default `Subnautica2-Win64 UnrealEditor AutomationTool UnrealBuildTool ShaderCompileWorker sn1build Subnautica.exe` (SN1 counts as heavy; a hand-started SN1 game makes the verdict BUSY). **Gap (2026-11-22):** a Python job such as `sn1_extract_terrain.py` is not a heavy process by image name, so its lock lapses after `SN2_LOCK_IDLE` (60 s) and another session could take it mid-run (seen: the `sn1extract` lock was gone by the end of a 40 s extraction). Fix still open: e.g. a `heavy_lock.sh hold <pid>` that counts that PID as heavy while it lives; until then, keep the extractor runs short or refresh the lock.
- **Wired into:**
  - `launch_game.sh`: acquire game, exit 4 if busy. `relaunch_on_exit.sh` goes through it and re-acquires as the same owner.
  - `install_mod.sh`: acquire game, exit 4. The mod files in `<GameDir>` are shared state.
  - `autotest.sh` and `autotest_retry.sh`: wait up to `SN2_LOCK_WAIT` s (default 3600), exit 2 on timeout, release on exit. A run inside autotest_retry reuses the held lock.
  - `src/modkit/tools/cook_install.sh`: what=cook, waits like autotest, exit 4.
  - `src/modkit/tools/launch_editor.sh` (new): acquires editor, then starts `Launch-Editor.cmd` unless an editor is already open.
  - `ue_run.py`: exit 5 if this session does not hold the lock. `SN2_LOCK_SKIP=1` bypasses the check.
  - Double-clicking `Launch-Editor.cmd` bypasses the lock, but the running editor still makes other sessions wait.
- **Rules:**
  - Acquire before starting a heavy job.
  - Close what you started: quit the game, or close the editor (`ue_run.py -c "unreal.SystemLibrary.quit_editor()"` is UNTESTED).
  - Then `release`. Releasing while heavy processes still run prints a WARNING, and other sessions stay BUSY until those processes exit.
- **Not covered by the lock:** the modkit project content (two sessions editing assets between editor runs), SN2 saves, and `mods.txt` edits made outside install_mod.sh. Each session installs its mods right before it launches, as autotest does.
- **Status:**
  - **VERIFIED (2026-11-19, scratch `SN2_LOCK_DIR` tests, no game or editor started):** free; acquire; busy for a second owner; check 0/1; a waiter gets the lock after release; takeover from a dead PID; idle takeover; an unowned heavy process blocks; refresh (`what=game,editor`); `ue_run.py` exit 5 without the lock; `install_mod.sh` and `launch_game.sh` exit 4 while another owner holds it.
  - **UNTESTED:** real runs with the game or editor. Also UNTESTED: the `tasklist` image names during a cook (AutomationTool may show as `dotnet.exe`; if so, add it to `SN2_HEAVY_PROCS` after checking).

## User protocol (the tester drives the game)
- The tester presses all in-game keys; you cannot. Give exact key, place to stand/look, and what should happen.
- **No waiting at the main menu (user decision 2026-11-18).** The old rule "wait ~60 s at the menu before loading" is withdrawn: an end user must not have to wait, so the lobby→world GC-watchdog crash (crash table below) is an open **bug to fix**, not something to work around. The rule never worked reliably anyway: the 2026-11-17 17:27:51 crash happened ~59 s after the menu appeared. Tests click through the menu as soon as it is visible; every crash is recorded in the crash table with its delay after the menu. Lobby banner in log: `not in L_Main (World /Game/Maps/L_ClientLobby...)`.
- the test save loads at about **(-331747, 420670, -2072)** (near the surface, Axum/AR area, ~21 m deep). Earlier tests used the Coral Gardens area around (-204942, 432071, -24066).
- **Console commands are disabled in the test save** ("commands are disabled"), so `Warp`, `SpawnCreature`, etc. are unavailable — implement movement/tests in Lua
  (e.g. F1 teleports via `Pawn:K2_SetActorLocation`).
- Back up saves before anything that could persist: `bash src/tools/backup_saves.sh`.
- Runtime edits vanish when the world reloads (respawn, menu, relaunch) — mods must re-apply on every world load (`ClientRestart` hook / sweep loop).

## UE4SS Lua rules (each learned from a failure)
- **Never put raw control characters in Lua source (2026-11-19 incident).** Run `20261119_201024_lmain_baseline` = FAIL_LOBBY after 189 s: `SN2AutoTest` did not load, UE4SS.log: `Error loading script: ...SN2AutoTest/Scripts/main.lua:215: unfinished string near '"['`. In `shortErr` the pattern had a real CR, LF and TAB inside the quotes instead of the backslash escapes; the file also had CRLF line endings. Cause (LOGGED): edits made with an inline Python/bash snippet whose command text had its backslash escapes expanded before Python saw them, and Python text-mode read/write on Windows turned LF into CRLF. Rules: write Lua with the Write/Edit tools, not inline shell/Python (if a patch script is needed, build escapes with chr(92) and open files in binary mode); repo Lua is LF only. Guards (2026-11-19, UNTESTED in game): `install_mod.sh` runs `src/tools/check_lua_ctl.py` on `Scripts/*.lua` and refuses (exit 5, prints file:line) on any CR or control byte except TAB/LF; the autotest driver watches UE4SS.log while waiting for the lobby and ends with `RESULT FAIL_LUA_LOAD <error line>` (+ `shots/stall_lua_load.png`, `windows_lua_load.txt`) on any `Error loading script ... SN2...` line; `autotest_retry.sh` never retries it. Caveat: it reads the whole UE4SS.log, so it assumes UE4SS truncates the log per launch.
- **Validity checks must be pcall-wrapped.** `o.IsValid ~= nil and o:IsValid()` threw `System: Global for __index doesn't exist.` on an actor that died mid-sweep
  (2026-11-16, caught by the sweep's pcall → one skipped sweep). `isValid` in SN2TerrainEdit now does `pcall(function() return o:IsValid() end)`.
- **Don't pass/return complex structs through UFunctions from Lua** (structs containing FText, TSoftObjectPtr, FGameplayTagContainer, arrays of
  such): `SN2AdaptationsPlayerStateComponent:GetAdaptations()` crashed UE4SS.dll (AV READ 0x10) twice on 2026-11-16. Plain structs (FVector,
  FGameplayTag as `{ TagName = FName("...") }`) are fine.
- **Never call UFunctions on class-default objects** (`Default__…`, returned by `FindAllOf`) — crashed the game (12:55, access violation in the exe). Filter with a name check.
- **`ExecuteWithDelay` / `LoopAsync` callbacks run off the game thread.** Wrap engine calls in `ExecuteInGameThread(function() … end)`; `LoadAsset` refuses otherwise
  ("can only be called from within the game thread"). `RegisterKeyBind` and `RegisterHook` callbacks are already on the game thread.
- Out-params: pass a table variable and read it after (`local O, E = {}, {}; a:GetActorBounds(false, O, E, false)`).
  Exception found: `AppendBuffersToMesh` rejects this ("no table was on the stack") — unresolved.
- Structs are plain tables (`{X=,Y=,Z=}`; transform `{Rotation={X,Y,Z,W}, Translation={...}, Scale3D={...}}`); enums are integers; `nil` for optional object params.
- UE 5.6 line traces: `HitResult.HitObjectHandle.ReferenceObject:Get()` may return the hit **component**; use `:GetOwner()` to reach the actor.
- Reading arbitrary property values can fail; reading names/types via `Class:ForEachProperty` is safe. Simple value types read fine.
- `StaticFindObject(path)` only finds loaded objects; load with `LoadAsset(path)` on the game thread.
- Spawning: `GameplayStatics:BeginDeferredActorSpawnFromClass(World, Class, T, 1, Owner, 0)` → configure → `FinishSpawningActor(Actor, T, 0)`
  (both have older signatures without the trailing arg; code tries both).
- A spawned mesh whose bounding sphere contains the camera is invisible (back-face culling) — place beyond `mesh:GetBounds().SphereRadius`.
- Destroy + free: `actor:K2_DestroyActor()` then `KismetSystemLibrary:CollectGarbage()`; confirm with object counts before/after.

## Automated test runs (SN2AutoTest + autotest.sh) — built 2026-11-18
**Decision (user, 2026-11-18): every player action goes through simulated OS keyboard/mouse input (`src/tools/autotest_driver.py`, SendInput); the Lua mod `SN2AutoTest` is observe-only plus test hotkeys. No fixed wait at the main menu (see "User protocol").** The first design (Lua called `StartNewLocalGameWithOptions`, `SetControlRotation`, `QuitGame`, `HighResShot`) was replaced the same day; its facts are kept below.

**How to run** (use `run_in_background: true`; a 40-shot run takes ~6 min; nobody may touch the PC; the game window must stay visible on the primary 1920x1080 screen):
`bash src/tools/autotest_retry.sh <plan>` (up to 3 attempts, retries only after `CRASH`, adds no waits; prints `RETRY_SUMMARY plan attempts crashes final`) or one attempt `bash src/tools/autotest.sh <plan>`. Exit code 0 only for `DONE` with all shots.
autotest.sh: abort if the game runs, `backup_saves.sh`, install SN2AutoTest + SN2Census, `autotest_driver.py arm` writes `<ue4ss Mods>/SN2AutoTest/run/active_plan.lua`, delete `UE4SS.log`, `launch_game.sh`, start `autotest_driver.py run <plan.json>` in the background, poll every 5 s: driver finished -> result from its `RESULT` line (+ taskkill after 60 s); game process gone and driver `RESULT DONE` -> `DONE` (the Exit-game clicks close the game before the driver returns); game gone otherwise -> `CRASH` (new folder in `%LOCALAPPDATA%\Subnautica2\Saved\Crashes\` or new `ue4ss\crash_*.dmp`) or `EXITED`; 15 min -> `TIMEOUT`. Driver results: `DONE FAIL_LOBBY FAIL_NOPAWN FAIL_FOCUS`.
**Plan format** `src/mods/SN2AutoTest/plans/<name>.json`: `{name, worldLevel (path or null = the ModActor's L_SN2World), start "new"|"load", loadSlot, settleSeconds (15), waypoints:[{name, offset:[x,y,z] cm | absent}]}`. Offsets are added to the first `BP_StaticLifepod_Surface_C` location (works in L_Main and L_SN2World); no offset = recorded settled spawn. `plans/menus.json` holds the button centres (named steps) and the mouse calibration. The driver converts waypoints/worldLevel into `run/active_plan.lua` (Lua table); Lua renames it to `active_plan.consumed.lua` on load (a crash never leaves it armed); no plan file = `[SN2AutoTest] idle (no plan)` and no hooks.
**Output** `<Workspace>\autotest\<YYYYMMDD_HHMMSS>_<plan>\`: `shots\` (`<wp idx 2d>_<wp>_k<k>.png` = 8 views per waypoint, plus `menu_<nn>_<screen>.png` after every menu click and `00_nopawn.png`), `manifest.tsv` (idx waypoint k yaw pawnXYZ camXYZ unixTime file; **yaw/pawn/cam are the MEASURED values from the STATE log line**), `driver.log`, `UE4SS.log`, `Subnautica2.log`, `census\` (auto report 20 s after arming + one at t=15 s), `crash\`, `result.txt`, `summary.txt` (result, shots expected/found, per-shot luminance + diff to previous with BLACK/UNCHANGED flags, key log lines, first/last census sample, crash info), `shot_stats.txt`, `sheets\<idx>_<wp>.png` (4x2 contact sheet, 480x270 tiles, caption `k=.. yaw=..`; `autotest_sheets.py`), `plan.json`.
**Run flow (driver):** wait `[SN2AutoTest] WORLD L_ClientLobby` -> menu ready = two screen captures 1 s apart differ < 0.5 (took 3-21 s after the lobby line) and, with `worldLevel`, the `worldLevel set` line (Lua sets it 2 s after the lobby line) -> menu clicks -> `PAWN possessed` (<=240 s) -> settle 15 s -> per waypoint: teleport key, STATE, turn to front yaw / pitch 0 with the mouse (re-measure, up to 4 corrections, tolerance 3 deg), then for k=0..7: teleport key again, wait 3 s (k=0) / 0.8 s, screenshot, STATE (measured values to the manifest), mouse +45 deg -> Escape-menu quit -> `taskkill` fallback after 60 s.

**Input injection facts (VERIFIED 2026-11-18, autotest screenshots + log)**
- UE4SS hotkeys fire on SendInput scan-code key events: `Ctrl+F11` (STATE) and the teleport keys worked every time (scan codes via `KEYEVENTF_SCANCODE`, modifiers held around the key).
- Menu clicks register via `MOUSEEVENTF_MOVE|ABSOLUTE` (x*65535/1919), 0.25 s hover, left down 80 ms / up. **A click on a screen that is still animating in is sometimes ignored** -> the driver repeats the click (max 3) while the screen did not change (`retry` steps).
- Mouse look works with relative `MOUSEEVENTF_MOVE` in chunks of 40 counts every 12 ms: **4.571 counts per degree for yaw and for pitch** (2000 counts = 437.6 deg; +dx = yaw increases (turn right); +dy = pitch decreases (look down); pitch clamps at +-89.9; measured error after one correction <= 0.1 deg over 8 x 45 deg turns). Calibration method: `Ctrl+F11` -> move 600 counts -> `Ctrl+F11`, wrap handled.
- **Game-bound keys:** `F8` opens the in-game **Feedback panel**; while it is open mouse look is dead and screenshots show the panel (first lmain_baseline run, teleport keys Ctrl+F6..F10: waypoints 3-5 mostly showed the panel, yaw stuck at 90.03). Teleport hotkeys are therefore **Ctrl+Shift+Z / X / C / V / B** (waypoints 1-5), STATE is **Ctrl+F11**. Escape opens the pause menu.
- `ImageGrab.grab()` (Pillow, DPI aware) captures the game at 1920x1080, not black (mean luminance 23-54 in game). The `HighResShot` engine method and the req/ack capture helper were dropped (engine method never tried); dxcam not needed.
- Focus: `SetForegroundWindow` with an Alt tap + `AttachThreadInput`, `GetForegroundWindow` checked before every input (abort = `FAIL_FOCUS`, exit 3). The window is gone after the last Exit click (expected, treated as DONE).
- The UE4SS GUI console (`GuiConsoleVisible = 1`) is a separate window; the driver refocuses the game before each action and screenshot.
