# Runbook — how to change the game and test it

## The loop (every change)
1. Edit `src\mods\<Mod>\Scripts\main.lua` (and `data\` files). For large edits, write a small Python patch
   script that asserts its anchor strings occur exactly once, then replaces — this caught several mismatches.
2. Install: `bash src/tools/install_mod.sh <Mod>` (copies Scripts + data into the game and the bundle, registers in `mods.txt`).
3. **UE4SS reads Lua only at game launch.** Reloading the save does NOT pick up changes. Hot-reload is deliberately OFF (see Crashes).
   If the game is running: start `bash src/tools/relaunch_on_exit.sh` with `run_in_background: true`, then ask the tester to quit.
   It relaunches via `launch_game.sh` (Steam `-applaunch`, see "Launching through Steam" below) after a confirmed exit. If not running: `bash src/tools/launch_game.sh`.
4. Watch the log with the Monitor tool: command `bash src/tools/watch_log.sh`, `timeout_ms: 1800000`; re-arm on expiry.
   Monitors die when the Claude session restarts — re-arm after any restart. Keep the filter quiet (per-sweep lines flood the chat).
5. The tester loads the save and presses keys; you read results from the log and ask the tester what is visible. The log proves calls ran, only the tester can confirm visuals/physics.

## Parallel sessions: the heavy lock (`src/tools/heavy_lock.sh`, built 2026-11-19)
RAM fits only one heavy job at a time, so several Claude sessions share a single lock. Which jobs are heavy is listed in `CLAUDE.md` "Parallel sessions: one heavy job at a time" (the single source of truth; changing it also means updating `SN2_HEAVY_PROCS` in `heavy_lock.sh`). SN1 launches were added by user rule 2026-11-22; `sn1_run.sh` takes the lock as `sn1`.
- **Commands:**
  - `bash src/tools/heavy_lock.sh status` shows the holder, the running heavy processes and a verdict (FREE / HELD / BUSY).
  - `acquire <game|editor|cook|build|sn1> [--wait S] [--note T]`: exit 0 means this session holds the lock. `--wait` polls every `SN2_LOCK_POLL` s (default 15). Run long waits with `run_in_background: true`. Re-acquiring a lock you hold refreshes it and adds `<what>`.
  - `release [--force]`: `--force` takes another session's lock and needs the user's say-so.
  - `check`: exit 0 if this session holds the lock (also renews the lease).
  - `renew`: holder only, resets the lease (exit 1 if not yours). `hold [--every S] [--max S]`: holder only; a foreground heartbeat (run it with `run_in_background: true`) that renews every S s (20) for at most `--max` s (3600), and ends by itself when you released, lost the lock or your claude.exe is gone. Use it across a long job that is not a heavy process (Python extractor) or a long gap between steps.
- **State and identity:**
  - The lock lives in `<Workspace>/locks/heavy.info`, as key=value lines: owner, owner_pid, what, note, since, seen, renewed. Waiters queue as files in `<Workspace>/locks/queue/` (name `<epoch-ns>.<owner>`, content owner, mtime = last poll).
  - Every read-modify-write runs under an atomic `mkdir` guard, `.guard`. A guard older than 60 s is removed.
  - Events are logged to `<Workspace>/locks/history.log`.
  - `SN2_LOCK_DIR` overrides the folder, for tests.
  - The owner is `SN2_LOCK_OWNER` (PID in `SN2_LOCK_OWNER_PID`), otherwise `claude-pid-$CLAUDE_PID`. Each Claude session is its own claude.exe; in-process subagents share their parent's lock.
- **The lock counts as free when any of these holds (lease design, 2026-11-28):**
  - nobody holds it
  - the holder's `owner_pid` process is gone: freed at once. `owner_pid` is the claude.exe of a normal session; a named owner (`SN2_LOCK_OWNER=<agent>`) has none unless `SN2_LOCK_OWNER_PID` is set, so subagents rely on the lease below
  - lease expired: no heavy process running and no renewal (`acquire` by the holder, `check`, `renew`, `hold`) for `SN2_LOCK_IDLE` s (default 600). This frees a holder that forgot to release within 10 min. A holder whose heavy process is running is never idle, so gaps up to 10 min between your own steps (install, launch, read results, edit, relaunch; editor script, cook) keep the lock; for longer gaps or Python jobs run `hold` in the background.
  - History: the lock was 600 s until 2026-11-19, 60 s, then 10 s on 2026-11-28; 10-60 s lost the lock in the gaps between a session's own steps (`history.log` 13:23-13:57 showed two sessions alternating TAKEOVER every 15 s, each cutting the other's multi-step job).
- **Unowned heavy processes:** if nobody holds the lock but a heavy process is running, the verdict is BUSY. This catches an orphan or a game or editor started by hand. Only `acquire editor` may adopt an already-open UnrealEditor / ShaderCompileWorker.
- **Fair order:** `acquire --wait N` (N>0) joins a FIFO queue and keeps its place on every poll; an entry not refreshed for `SN2_LOCK_QTTL` s (max(4*POLL, 60)) is dropped as dead. While a live waiter is queued, nobody else can take a free or stale lock: a `--wait 0` caller (newcomer, or the releasing holder re-acquiring) is refused (exit 1, so callers' exit 4 / 2 paths are unchanged) and the queue head takes it at its next poll (at most `SN2_LOCK_POLL` s).
- **Replacing the script safely:** the whole script is one function called on the last line. Write a temp file next to it and `mv` it over `heavy_lock.sh` (never edit in place); running copies keep the old inode. VERIFIED (2026-11-28): an old-version `acquire --wait` loop survived an `mv` over its script and later acquired the lock. Old loops still apply the old 10 s idle rule until they end (they ignore `renewed`, but `renew`/`hold` also write `seen`, which they honour).
- **Gap: subagents share their parent's lock identity. FAILED (2026-11-26, runs `autotest/20261126_191722_samples` and `20261126_191727_brownwater_pp`):** the owner id is `claude-pid-<CLAUDE_PID>`, and an in-process subagent has the same claude.exe pid as the session that spawned it. The planner held the lock (`acquire game`) and started a samples autotest; 5 s later its investigator subagent's `autotest.sh` "acquired" the same lock (same owner) and launched a second game. Both runs ended `FAIL lobby not reached` (19:22:41). Rule until a code fix: a subagent that may run heavy jobs sets its own `SN2_LOCK_OWNER=<agent name>` on every heavy command, and the parent does not start heavy jobs while such a subagent is running. Still open (UNTESTED idea): `acquire` by the same owner refuses while a heavy process is running that this command did not start.
- **Heavy process names:** image-name prefixes in `SN2_HEAVY_PROCS`, default `Subnautica2-Win64 UnrealEditor AutomationTool UnrealBuildTool UnrealPak ShaderCompileWorker sn1build Subnautica.exe` plus `dotnet.exe` running AutomationTool/UnrealBuildTool (SN1 counts as heavy; a hand-started SN1 game makes the verdict BUSY). **Python jobs (e.g. `sn1_extract_terrain.py`) are not heavy processes by image name:** they keep the lock only through the lease or `hold` (run `heavy_lock.sh hold` in the background for jobs over a few minutes).
- **Wired into:**
  - `launch_game.sh`: acquire game, exit 4 if busy. `relaunch_on_exit.sh` goes through it and re-acquires as the same owner.
  - `install_mod.sh`: acquire game, exit 4. The mod files in `<GameDir>` are shared state.
  - `autotest.sh` and `autotest_retry.sh`: wait up to `SN2_LOCK_WAIT` s (default 3600), exit 2 on timeout, release on exit. A run inside autotest_retry reuses the held lock.
  - `src/modkit/tools/cook_install.sh`: what=cook, waits like autotest, exit 4.
  - `src/modkit/tools/launch_editor.sh`: acquires editor, then starts `Launch-Editor.cmd` unless an editor is already open.
  - `ue_run.py`: exit 5 if this session does not hold the lock. `SN2_LOCK_SKIP=1` bypasses the check.
  - Double-clicking `Launch-Editor.cmd` bypasses the lock, but the running editor still makes other sessions wait.
- **Rules:**
  - Acquire before starting a heavy job.
  - Close what you started: quit the game, or close the editor (`ue_run.py -c "unreal.SystemLibrary.quit_editor()"` is UNTESTED).
  - Then `release`. Releasing while heavy processes still run prints a WARNING, and other sessions stay BUSY until those processes exit.
- **Not covered by the lock:** the modkit project content (two sessions editing assets between editor runs), SN2 saves, and `mods.txt` edits made outside install_mod.sh. Each session installs its mods right before it launches, as autotest does.
- **Status:**
  - **VERIFIED (2026-11-19, scratch `SN2_LOCK_DIR` tests, no game or editor started):** free; acquire; busy for a second owner; check 0/1; a waiter gets the lock after release; takeover from a dead PID; idle takeover; an unowned heavy process blocks; refresh (`what=game,editor`); `ue_run.py` exit 5 without the lock; `install_mod.sh` and `launch_game.sh` exit 4 while another owner holds it.
  - **FAILED (2026-11-28, `<Workspace>/locks/history.log` 13:13:53), now fixed:** during a cook the lock saw no heavy process. UAT runs as `dotnet.exe AutomationTool.dll BuildCookRun ...` and the pak step as `UnrealPak.exe`; neither image name matched `SN2_HEAVY_PROCS`. After 10 s idle another session took the lock over and launched the game while the cook ran. `cook_install.sh` then refuses the install ("game is running").
  - **Fix (2026-11-28):** `heavy_lock.sh` now counts `UnrealPak` as heavy.     - **VERIFIED (2026-11-28):** `status` showed `dotnet:AutomationTool` during a live cook.
    - **UNTESTED:** a full cook with the fixed script, i.e. no takeover across the cook → pak → install stages.
  - **Gotcha (2026-11-28):** never edit a running shell script in place (`cook_install.sh`, `autotest.sh`, ...): bash reads the file as it executes and the running copy dies with `syntax error near unexpected token` (a cook's AttachTo guard and install were skipped that way). Replace it with temp file + `mv`, as `heavy_lock.sh` is built to allow.
  - **Lease + queue (2026-11-28), tests `bash src/tools/test_heavy_lock.sh` (scratch `SN2_LOCK_DIR`, fake heavy process, no game/editor):** **VERIFIED (2026-11-28, 38 of 38 checks passed):** a gap inside the lease keeps the lock; an expired lease is taken over; `renew`, `check` and the `hold` heartbeat extend it; a dead `owner_pid` is freed at once and a live one is not; a running heavy process keeps the lock past the lease; an unowned heavy process blocks and `acquire editor` adopts an open editor; FIFO order B then C, the releasing holder and a newcomer are refused while someone is queued; a stale holder goes to the queue head; a dead queue entry is pruned; exit codes 0/1/2 unchanged. **UNTESTED:** behaviour in real multi-session use (callers were not changed: `autotest`, `cook_install`, `install_mod`, `launch_game` still refresh by re-acquiring).

## User protocol (the tester drives the game)
- The tester presses all in-game keys; you cannot. Give exact key, place to stand/look, and what should happen.
- **No waiting at the main menu (user decision 2026-11-18).** The old rule "wait ~60 s at the menu before loading" is withdrawn: an end user must not have to wait, so the lobby→world GC-watchdog crash (crash table below) is an open **bug to fix**, not something to work around. The rule never worked reliably anyway (a crash happened ~59 s after the menu appeared). Tests click through the menu as soon as it is visible; every crash is recorded in the crash table with its delay after the menu. Lobby banner in log: `not in L_Main (World /Game/Maps/L_ClientLobby...)`.
- The test save loads at about **(-331747, 420670, -2072)** (near the surface, Axum/AR area, ~21 m deep). Earlier tests used the Coral Gardens area around (-204942, 432071, -24066).
- **Console commands are disabled in the test save** ("commands are disabled"), so `Warp`, `SpawnCreature`, etc. are unavailable — implement movement/tests in Lua
  (e.g. F1 teleports via `Pawn:K2_SetActorLocation`).
- Back up saves before anything that could persist: `bash src/tools/backup_saves.sh`.
- Runtime edits vanish when the world reloads (respawn, menu, relaunch) — mods must re-apply on every world load (`ClientRestart` hook / sweep loop).

## UE4SS Lua rules (each learned from a failure)
- **Never put raw control characters in Lua source (2026-11-19 incident).** Run `20261119_201024_lmain_baseline` = FAIL_LOBBY after 189 s: `SN2AutoTest` did not load, UE4SS.log: `Error loading script: ...SN2AutoTest/Scripts/main.lua:215: unfinished string near '"['`. In `shortErr` the pattern had a real CR, LF and TAB inside the quotes instead of the backslash escapes; the file also had CRLF line endings. Cause (LOGGED): edits made with an inline Python/bash snippet whose command text had its backslash escapes expanded before Python saw them, and Python text-mode read/write on Windows turned LF into CRLF. Rules: write Lua with the Write/Edit tools, not inline shell/Python (if a patch script is needed, build escapes with chr(92) and open files in binary mode); repo Lua is LF only. Guards (2026-11-19, UNTESTED in game): `install_mod.sh` runs `src/tools/check_lua_ctl.py` on `Scripts/*.lua` and refuses (exit 5, prints file:line) on any CR or control byte except TAB/LF; the autotest driver watches UE4SS.log while waiting for the lobby and ends with `RESULT FAIL_LUA_LOAD <error line>` (+ `shots/stall_lua_load.png`, `windows_lua_load.txt`) on any `Error loading script ... SN2...` line; `autotest_retry.sh` never retries it. Caveat: it reads the whole UE4SS.log, so it assumes UE4SS truncates the log per launch.
- **`MaterialInstanceDynamic:K2_GetScalarParameterValue("Name")` from Lua kills the game thread (FAILED 2026-11-27, run `20261127_173849_uwab_lmain`: CRASH, `crash_2026_11_27_17_39_51.7525699.dmp`, the call after the preceding log line never returned).** Read the parameters from the `ScalarParameterValues` / `VectorParameterValues` arrays (own overrides) and walk `.Parent` for inherited ones (`SN2AutoTest/data/uwa.lua`, VERIFIED 2026-11-27). `CreateDynamicMaterialInstance(0, parentMaterial, FName("x"))` and `SetScalarParameterValue(FName("x"), v)` / `SetVectorParameterValue(FName("x"), {R=,G=,B=,A=})` worked (VERIFIED 2026-11-27, run `20261127_175122_uwab_sn2`, values read back from the arrays).
- **Lua facts from the water A/B (2026-11-27, investigator-water3):** runtime spawn of a Blueprint actor class works with the same recipe as a StaticMeshActor (`gs:BeginDeferredActorSpawnFromClass(world, cls, T, 1, pawn, 0)`, set UPROPERTYs, `gs:FinishSpawningActor(a, T, 0)`; the BP construction script and native `RecreateMaterials` then run). `comp:SetMaterial(0, mid)` takes a MID owned by another component. `_G.X = v` written inside an `SN2AutoTest` verb persists to later verbs. A runtime MID on a biome-tracked region is rewritten by the native tracker within seconds (`CurrentWaterBodyIndex` / `CurrentWaterBodyBlendType`), so write test values on an untracked actor. `GetStaticMesh()`, `IsRegistered()`, `IsRenderStateCreated()`, `HasValidSceneProxy()` and `Bounds` fields give nothing usable from Lua here. `ForEachProperty` over the class chain + reading only number/boolean values is a safe generic property dump (`uwa8`, VERIFIED 2026-11-27, 224 + 68 props, no crash).
- **UE4SS type-specific property accessors are unchecked casts (FAILED 2026-11-28, run `20261128_120333_buildprobe_dump`: game crash after `SN2BuilderTool.LogMissingRequirementAnalytics`).** `prop:GetPropertyClass()`, `GetStruct()`, `GetEnum()` and `GetInner()` do not check the property type; calling one on the wrong `FProperty` type crashed the game thread. Read `prop:GetClass():GetFName():ToString()` first and call only the accessor that matches (`ObjectProperty` / `ClassProperty` / `Soft*` -> `GetPropertyClass`, `StructProperty` -> `GetStruct`, `EnumProperty` -> `GetEnum`, `ArrayProperty` -> `GetInner`), and read plain value types only. Reusable code: `propType()` in `src/mods/SN2AutoTest/data/buildprobe.lua`.
- **Lua facts from the builder probe (2026-11-28, `buildprobe.lua`, VERIFIED in game):** `mesh:AddAssetUserDataOfClass(cls)` + `mesh:GetAssetUserDataOfClass(cls)` work on a loaded StaticMesh (interface functions), `ud.DataAssets[1] = da` sets a TArray element; `cdo("/Script/UWEAssetRegistry.UWEAssetUserData")` finds the class; `GameplayTagContainer.GameplayTags:ForEach(function(_, t) t:get().TagName:ToString() end)` reads tags; `comp:GetCollisionResponseToChannel(n)` works (0 ignore, 1 overlap, 2 block); the builder tool actor is found with `FindAllOf("SN2BuilderTool")` after the pawn equips it, `tool:ActivateAction(<DA_*_ItemBrushData>)` starts placement mode and the ghost follows the camera.
- **Test-running gotchas (2026-11-28, investigator):** (1) `TaskStop` on a Bash chain `acquire && install && autotest.sh` that has already launched the game kills only the shell: the game, the hidden holder and the driver keep running as orphans (the run folder gets no `result.txt` copy of UE4SS.log and no slot cleanup; check `slots_pre.txt` against the save folder). Never stop such a chain; wait for it. (2) Heavy lock takeover now happens after about 10-60 s without a heavy process (history.log showed `idle 16 s > 10 s`), so `install_mod.sh` + the launch must follow `acquire` immediately in one command, and another session's calibration run can start between two of your runs. (3) A second chain started while the first one's game is up fails `game is running - abort` or FAIL_LOBBY: check `tasklist` first. (4) `autotest_retry.sh` is the right entry point on this machine: 2 of 5 runs on 2026-11-28 ended in the lobby GC-watchdog CRASH and the retry completed.
- **Backslashes in Bash-tool heredocs get mangled (VERIFIED 2026-11-23, twice in `01`):** a `python - <<'PY' ... PY` heredoc run through the Bash tool turned `\a`, `\r`, `\t` and `\202` in Windows paths into control characters (BEL, CR, TAB, U+0082), even with a quoted heredoc and Python raw strings, and the damage landed in research files. Rule: never put backslashes in heredoc text that ends up in a file. Write the editing script with the Write tool, build backslashes with `chr(92)`, or use the Edit tool. After a scripted edit, check with `python -I -c "import re;s=open(p,encoding='utf-8').read();print([ascii(s[m.start()-20:m.start()+20]) for m in re.finditer('[\x00-\x08\x0b-\x1f\x7f-\x9f]',s)])"`.
- **`FindFirstOf` / `FindAllOf` / `:GetWorld()` never return nil for "not found": they return an INVALID UObject wrapper, and calling a method on it can be a native null dereference that `pcall` cannot catch (VERIFIED 2026-11-26, three minidumps: AV READ 0x0 at `UE4SS.dll+0x350206` inside the `UObject::GetWorld` wrapper, from `FindFirstOf("PlayerController"):GetWorld()` in a LoadMap pre-hook at the first Browse, where no PlayerController exists yet).** Always test `pcall(function() return o:IsValid() end)` first, and do not touch world / controller objects from a LoadMap hook without it. `require("UEHelpers").GetWorld()` is the safe way to get the world (diag.lua).
- **Validity checks must be pcall-wrapped.** `o.IsValid ~= nil and o:IsValid()` threw `System: Global for __index doesn't exist.` on an actor that died mid-sweep
  (2026-11-16, caught by the sweep's pcall → one skipped sweep). Use `pcall(function() return o:IsValid() end)`.
- **Don't pass/return complex structs through UFunctions from Lua** (structs containing FText, TSoftObjectPtr, FGameplayTagContainer, arrays of
  such): `SN2AdaptationsPlayerStateComponent:GetAdaptations()` crashed UE4SS.dll (AV READ 0x10) twice on 2026-11-16. Plain structs (FVector,
  FGameplayTag as `{ TagName = FName("...") }`) are fine.
- **Never call UFunctions on class-default objects** (`Default__…`, returned by `FindAllOf`) — crashed the game (12:55, access violation in the exe). Filter with a name check.
- **`ExecuteWithDelay` / `LoopAsync` callbacks run off the game thread.** Wrap engine calls in `ExecuteInGameThread(function() … end)`; `LoadAsset` refuses otherwise
  ("can only be called from within the game thread"). `RegisterKeyBind` and `RegisterHook` callbacks are already on the game thread.
- Out-params: pass a table variable and read it after (`local O, E = {}, {}; a:GetActorBounds(false, O, E, false)`).
  Exception found: `AppendBuffersToMesh` rejects this ("no table was on the stack") — unresolved.
- Structs are plain tables (`{X=,Y=,Z=}`; transform `{Rotation={X,Y,Z,W}, Translation={...}, Scale3D={...}}`); enums are integers; `nil` for optional object params.
- UE 5.6 line traces: `HitResult.HitObjectHandle.ReferenceObject:Get()` may return the hit **component**; use `:GetOwner()` to reach the actor.
- Reading arbitrary property values can fail; reading names/types via `Class:ForEachProperty` is safe. Simple value types read fine.
- `StaticFindObject(path)` only finds loaded objects; load with `LoadAsset(path)` on the game thread.
- Spawning: `GameplayStatics:BeginDeferredActorSpawnFromClass(World, Class, T, 1, Owner, 0)` → configure → `FinishSpawningActor(Actor, T, 0)`
  (both have older signatures without the trailing arg; code tries both).
- A spawned mesh whose bounding sphere contains the camera is invisible (back-face culling) — place beyond `mesh:GetBounds().SphereRadius`.
- Destroy + free: `actor:K2_DestroyActor()` then `KismetSystemLibrary:CollectGarbage()`; confirm with object counts before/after.
- Do not keep UObject lists across seconds of streaming (stale objects crash UE4SS, see crash table): re-find objects before use. Do nothing periodic in `L_ClientLobby` / during map loads (precaution; it is not the cause of the GC watchdog, see below).

### Start-up hang (the game's unclean-exit dialog; cause VERIFIED 2026-11-18 from the logs of every run + the tester's report of the dialog text)
- The game has a crash watchdog (`LogUWECrashWatchdog`). While running it keeps two mark files in `%LOCALAPPDATA%\Subnautica2\Saved\`: `running.dat` (removed on a clean exit) and `beforelobby.dat` (removed once the lobby is reached). At start-up it logs `Warning: Running mark exists when starting, last exit was unclean` and/or `Warning: Lobby mark exists when starting, last load did not reach the lobby`.
- **When both marks exist** the game opens a modal Windows dialog and the main thread waits on it (`ThreadState=Wait WaitReason=LpcReply`, black game window). In the log it sits between `LogMercuna: Display: Unreal Engine version: 5.6.1` and `LogGameInput: GameInputBase module startup...` (normal gap ~60 ms). Only the running mark (`beforelobby.dat` absent) = warning, no dialog.
- Loop: game force-killed before the lobby (`FAIL_LOBBY` -> `taskkill /F`) -> both marks stay -> next launch shows the dialog -> nobody answers -> `FAIL_LOBBY` -> kill again.
- **Dialog (VERIFIED 2026-11-18, `dialogs` subcommand + screenshot):** top-level window of the game process, class `#32770`, title `Error`, children `Button` + `Edit` (the message is a read-only **Edit**: `GetWindowText` returns empty; the driver reads it with `WM_GETTEXT` via `SendMessageTimeoutW`). Text: "Your game might not have exited correctly the last time you played. Verify your system meets the minimum requirements, and if this persists, update graphics drivers, or try resetting or lowering the game settings." **Only one button: `OK`** (screen rect (1091,586)-(1164,610)); no "reset settings" option exists.
- **Rule:** the harness exits the game cleanly whenever it can, and detects this dialog after launch and dismisses it only through a button that just continues (`OK` / `Continue` / `Close`). It must never pick a reset / lower-settings option (capture resolution must stay 1920x1080). Never delete the mark files (Saved is off-limits).
- **Driver behaviour (`src/tools/autotest_driver.py`):** `find_game_dialogs()` lists visible `#32770` top-level windows of the game pids (title, texts, buttons with `&` removed, hwnd, rect); subcommand `dialogs` prints them. `run_plan` checks each second while waiting for the lobby line (300 s): prints `[driver] DIALOG title=.. text=.. buttons=[..]`, saves `shots/menu_00_dialog.png`, clicks a matching button, prints `[driver] DIALOG_DISMISSED <label>`, waits up to 5 s. No such button = `RESULT FAIL_DIALOG buttons=[..]`, exit 4. At most 3 dialogs per run.
